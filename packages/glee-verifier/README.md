# GLEE verifier client prototype

`@gleephoenix/verifier` is a GLEE-owned Node.js client for the existing GLEE
Acceptance v0 service, with an offline receipt authenticator and CLI. It has
**zero runtime or peer dependencies**, and runs without AgentKit. It extracts
the protocol implemented by [Coinbase PR #1560](https://github.com/coinbase/agentkit/pull/1560)
at [revision d4aa34e](https://github.com/gleephoenixcrew/agentkit/tree/d4aa34e6d841da359ea008c262c7a9091e956ee4/typescript/agentkit/src/action-providers/glee-verifier).

The service already belongs to GLEE. This package makes the client independently
installable, testable, and maintainable; it does not implement a replacement
patch-analysis engine. The pending Coinbase PR remains an optional integration.

## Run the prototype

Node.js 22 or later is required. From this directory:

```sh
npm test
npm run demo
npm run smoke
```

No dependency installation is needed to run these commands. The demo verifies
stored PASS and FAIL receipts and rejects a changed result. Its receipts were
generated by the service code using a disposable test key and mocked settlement.
It performs no network request, payment, or new patch analysis.

The smoke test packs the package, installs that tarball offline in a temporary
app, confirms AgentKit is absent, imports the SDK and optional adapter, and
checks the installed CLI. PASS and FAIL use the service-generated fixtures;
INSUFFICIENT_EVIDENCE uses a separately signed synthetic fixture solely to check
verdict handling and exit code 2. It removes the temporary app afterward.

For a separate consumer, make a tarball and install the emitted filename:

```sh
npm pack --offline --ignore-scripts
# Run in your consumer app, using the actual tarball path printed above:
npm install --offline --ignore-scripts --no-audit --no-fund /absolute/path/gleephoenix-verifier-0.1.0-prototype.0.tgz
```

The manifest has `private: true`; this prototype is not an npm registry release.
The repository workflow tests Node 22 and 24 with no live wallet or paid calls.
A workflow file alone is not evidence that a remote run passed.

## Offline API

```js
import { readFile } from "node:fs/promises";
import { prepareRequest, authenticateDelivery } from "@gleephoenix/verifier";

const read = async path => JSON.parse(await readFile(path, "utf8"));
const request = await read("request.json");
const delivery = await read("delivery.json");
const trust = await read("operator-trust.json");

const prepared = prepareRequest(request);
console.log(prepared.requestHash, prepared.artifactHash, prepared.contractHash);
const authenticated = authenticateDelivery(delivery, request, trust);
console.log(authenticated.receipt_verified, authenticated.result.verdict);
```

`operator-trust.json` must supply `trustedReceiptPublicKeyHex` (64 hexadecimal
characters), `trustedPayTo` (approved Base recipient), and `payer` (expected
address). Establish these independently of the received challenge or receipt.
The bundled fixture's key and addresses are test data, never production defaults.
The service's public key-discovery endpoint can support a rotation review; its
response is not automatically a trusted pin.

Accepted requests contain `patch`, optional `path_policy.allowed_paths` and
`path_policy.banned_paths`, optional `assertions` (`type`, `pattern`, optional
`message`), and optional `job_id`. Unknown request, policy, and assertion fields
are rejected so a typo cannot silently weaken a contract. A bounded request
snapshot is serialized once; the same bytes are used for both HTTP submissions
and receipt validation. The client does not execute assertion regular expressions.

Prototype input limits are 512 KiB per serialized request, 256 KiB per patch,
32 assertions, 1–256 characters per assertion pattern, 128 entries per path
list, 512 characters per path entry, and 128 characters per job ID. The default
per-request network deadline is 10 seconds (configurable up to 60 seconds), and
the default response ceiling is 1 MiB. Wallet methods are caller-controlled
capabilities and are not forcibly interrupted by the network deadline.

## Direct service access

An unpaid quote check sends your patch to the configured service and validates
its payment challenge. It does not ask a wallet to sign:

```js
import { createVerifierClient } from "@gleephoenix/verifier";

const client = createVerifierClient({
  trustedPayTo: trust.trustedPayTo,
  trustedReceiptPublicKeyHex: trust.trustedReceiptPublicKeyHex,
  // endpoint defaults to https://gleephoenix.com/api/x402/verify/patch
});
const quote = await client.inspectQuote(request);
```

For paid use, the application must supply its own authorized wallet and the
explicit per-call ceiling. This prototype requires the frozen price and ceiling
of `"50000"` atomic USDC ($0.05), Base chain ID 8453, and the pinned recipient.

```js
const authenticated = await client.verifyPatch(request, {
  wallet: authorizedWallet,
  maxAmountAtomic: "50000",
});
```

The wallet interface is only `getChainId()`, `getAddress()`, and
`signTypedData(data)`; asynchronous results are supported. The client validates
x402 V2/exact terms, the Base USDC contract, token domain, price, recipient,
resource, and authorization timeout before signing. It rechecks wallet identity
and network, signs at most once per invocation, rejects redirects, bounds
response size and transport time, and does not retry a paid submission.

Signing authorization and funding remain with the caller. There is no private-key
loader, wallet dependency, funding operation, or paid CLI command. Tests use mock
wallets and mock HTTP. Live signing, settlement, current production trust pins,
and current service compatibility have not been established by this prototype.

If an error has `paymentMayHaveSettled: true`, a paid submission may have reached
the service without an authenticated result returning. Reconcile that attempt
before deliberately making another paid call. The field is uncertainty, not a
claim that settlement happened. Repeated application calls are separate attempts;
the SDK is not a cumulative budget manager or payment-reconciliation service.

## Optional AgentKit wallet adapter

```js
import { asGleeWallet } from "@gleephoenix/verifier/adapters/agentkit-wallet";

const wallet = asGleeWallet(existingAgentKitWalletProvider);
// Pass wallet to the same explicit, application-authorized verifyPatch call.
```

This adapter uses the provider's public wallet shape. It neither imports AgentKit
nor registers an AgentKit action provider. A structural mock is exercised by the
installation smoke; native framework registration and invocation remain separate
integration work. The existing PR contains the full action-provider integration.

## CLI

```sh
glee-verify demo
glee-verify prepare --request request.json
glee-verify authenticate --request request.json --delivery delivery.json --trust operator-trust.json
glee-verify quote --request request.json --trust operator-trust.json
```

Only `quote` accesses the network, using an unpaid POST. `--endpoint HTTPS_URL`
can override its configured endpoint. Authentication exit codes are:

| Exit | Meaning |
| --- | --- |
| 0 | Authenticated PASS |
| 1 | Authenticated FAIL |
| 2 | Authenticated INSUFFICIENT_EVIDENCE |
| 3 | Invalid input, invalid receipt, or command/transport error |

The other commands return 0 on successful completion; a quote success is not a
PASS verdict. JSON errors do not include an authenticated verdict.

## What the evidence means

`receipt_verified: true` means the pinned signer authenticated the exact request,
the content-bound result, and the receipt's stated payment terms. An authenticated
FAIL or INSUFFICIENT_EVIDENCE remains that verdict. Unbound response fields are
omitted from the public result.

The service checks unified-diff structure, path policy, static patterns, and
assertions over added lines. A static PASS does not prove that a patch applies,
tests pass, the program is correct, or the code is safe. The client authenticates
the service's result; it does not independently rerun those checks.

Acceptance v0 is content-addressed and has no expiration. Reusing a matching
receipt is valid evidence for the same content under that frozen methodology;
it is not evidence of a fresh execution or a new payment. Signed settlement
fields are the seller's attestation, not independent blockchain reconciliation.
Use distinct `job_id` values to distinguish requests where needed, while retaining
the exact request alongside its receipt.

The client pins schema `glee.acceptance_receipt.v0`, verifier version `0.1.0`,
and methodology hash
`0f3b0b09ab269ca98c862b20ec6eb39af4de14751bd6a3a1bd47d947b5ac0cb1`.
Protocol changes fail closed and require an intentional client update. Canonical
hashing matches the existing service's mixed sorted-JSON and ordered-JSON rules;
it is not a newly defined wire format. See [NOTICE](NOTICE) for exact source and
fixture provenance. This package is Apache-2.0; see [LICENSE](LICENSE).
